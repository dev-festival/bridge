# Bridge Surface Risk Register

This register covers planning and MVP implementation risks identified from `BRIDGE-SPEC.md` and the repository inspection on 2026-08-06. Likelihood and impact use **Low / Medium / High**. The named owner is a role, not an assigned person.

| ID | Risk | Likelihood | Impact | Mitigation / planned control | Owner | Trigger or evidence | Closure condition |
|---|---|---:|---:|---|---|---|---|
| R-01 | The current directory is not a Git worktree, so the required review/commit-per-sprint workflow cannot be followed. | High | High | Treat Git initialization or attachment to the intended remote as a pre-sprint prerequisite; verify a clean status at every sprint start and end. | Repository owner | `git status` reports “not a git repository.” | `git rev-parse --is-inside-work-tree` succeeds and the baseline planning commit exists. |
| R-02 | The repository has no source, tests, dependency manifests, lockfiles, or runnable commands. | High | High | Make Sprints 01-07 establish backend, database, provider mock, CLI, frontend, locks, docs, and canonical gates before feature work. | Lead engineer | Any feature sprint begins before its foundation dependency is green. | All eight canonical gates pass from a clean checkout at Sprint 07. |
| R-03 | A 20-30 minute execution target may encourage unfinished cross-layer work or skipped tests. | Medium | High | Size by capability and file boundaries first; use explicit exclusions and stop conditions; split a sprint rather than carrying partial work forward. | Sprint implementer | Expected production changes exceed roughly eight files, multiple migrations are needed, or a second workflow appears. | Each sprint ends runnable, reviewable, and green without work for the next sprint. |
| R-04 | Original source text could be overwritten by translations, generic PATCH handlers, or email edits. | Medium | High | Allowlist mutable fields, make message originals immutable, invalidate email derived content on source edits, and enforce transitions in services with negative tests. | Backend engineer | A request schema accepts `original_text` for an existing message or preserves approval after source edit. | Immutability and invalidation integration tests pass for conversation and email flows. |
| R-05 | Numerical values, equipment codes, drawing numbers, or business terms may change during translation. | High | High | Add terminology context plus deterministic pre/post preservation checks for numbers and identifier patterns; surface mismatches as warnings; never mutate originals. | Translation engineer | Mock or real provider returns a changed token such as `EQ-1048`, `0.05 mm`, or `WO123456`. | Required preservation tests and representative provider contract tests pass. |
| R-06 | Provider-generated reverse translations and warnings may be inconsistent or malformed. | High | Medium | Validate structured provider output with Pydantic, normalize unknown warning types, retain usable translations when validation feedback fails, and expose clear retry/error states. | Translation engineer | Missing fields, invalid JSON, unsupported warning types, or provider schema drift. | Parser unit tests cover malformed/partial results and application behavior is deterministic. |
| R-07 | A real provider failure could corrupt or erase a saved conversation or email draft. | Medium | High | Commit user-authored content before provider calls where appropriate; update derived fields transactionally only on validated success; test timeouts, retries, and rollback. | Backend engineer | Timeout, rate limit, network failure, or invalid provider response during translation. | Failure integration tests prove saved originals, drafts, recipients, and prior approvals remain intact as specified. |
| R-08 | Sensitive message text, credentials, or provider payloads may leak through logs, traces, or stored metadata. | Medium | High | Body-free structured logs by default, redaction filters, metadata allowlist, safe exception mapping, `.env` secrets, external-processing disclosure, and security review documentation. | Security owner | Logs contain bodies, authorization headers, API keys, raw provider errors, or unrestricted metadata. | Privacy tests pass and the release checklist contains no known secret/body exposure. |
| R-09 | Silent real-to-mock fallback could present fake text as a real translation. | Medium | High | Default to mock only when explicitly configured; allow development fallback only behind a named flag and visibly label the result/provider. Never use silent fallback in production mode. | Product + translation engineer | Real provider fails and UI shows an unqualified successful translation. | Provider/fallback contract tests and visible provider-state UI pass. |
| R-10 | Terminology conflicts across global, conversation, and email-draft scopes could yield nondeterministic output. | Medium | Medium | Most-specific scope wins; reject duplicate active terms within one scope; expose effective preserved terms with the translation. | Backend engineer | Two active entries match the same source term with different targets. | Precedence, duplicate, deactivate, and do-not-translate tests pass. |
| R-11 | Japanese language quality, professional tone, or manufacturing meaning may be inadequate despite passing technical tests. | High | High | Use realistic bilingual fixtures, structured warnings, reverse translation, editable output, explicit approval, and schedule bilingual domain review before production use. | Product owner | Native-speaker review finds tone, intent, or terminology errors. | A designated Japanese/English manufacturing reviewer signs off on the MVP scenarios. |
| R-12 | “Recipient language first” is ambiguous for mixed or unknown To-recipient preferences. | High | Medium | Apply ADR-011: auto-resolve only on unanimous known To preferences; otherwise require explicit order. CC never selects order. | Product owner | Mixed/unknown To preferences with recipient-first selected. | Domain/UI tests prove the user must resolve the order and both languages remain included. |
| R-13 | Signature selection or rendering may duplicate a signature, include the wrong profile content, or permit HTML injection. | Medium | High | Build one pure assembly model, append one selected signature after both language sections, escape HTML by default, and test all signature/order combinations. | Backend engineer | Output contains multiple signatures, raw user HTML, or signature embedded per language block. | Plain-text and HTML golden/structural tests pass for supported profiles and orders. |
| R-14 | The reverse translation could accidentally be included as a third outgoing email version. | Medium | High | Keep validation artifacts out of the renderer input model and assert their absence in preview/export tests. | Backend engineer | Preview or export contains reverse-translation text. | Negative renderer and end-to-end assertions pass. |
| R-15 | The UI could drift into a conventional chat layout and obscure the shared bilingual object. | Medium | Medium | Treat one shared message row as the component boundary; test side/direction labels and responsive relationships; review against product principles. | Frontend engineer | Original and translation render as unrelated alternating bubbles or one language is hidden. | Desktop and mobile UX acceptance checks pass for both source directions. |
| R-16 | SQLite behavior may mask PostgreSQL compatibility issues. | Medium | Medium | Use SQLAlchemy-portable types and constraints, migrations rather than runtime schema creation, UTC timestamps, and avoid SQLite-specific SQL. Add PostgreSQL CI only when deployment is selected. | Backend engineer | Raw SQLite SQL, implicit booleans/datetimes, or unsupported migration operations appear. | Architecture review finds no known SQLite-specific domain dependency; production DB testing is tracked before deployment. |
| R-17 | Single-user shortcuts may make later authentication/SSO migration costly. | Medium | Medium | Resolve local ownership through dependencies, store owner IDs, and never trust browser-provided ownership. Defer auth UI and roles. | Backend engineer | Hard-coded user ID appears in domain services or owner can be reassigned through normal API schemas. | Ownership tests pass and user resolution is isolated behind one application boundary. |
| R-18 | Frontend approval controls could be treated as the only state enforcement. | Medium | High | Backend services validate every transition and export-readiness rule; frontend only reflects server outcomes. | Backend engineer | Direct API calls can approve incomplete/warning-unacknowledged content or export an unready draft. | Negative API integration tests pass for all required preconditions. |
| R-19 | Clipboard/browser behavior differs across environments and may break HTML/plain-text copy. | Medium | Medium | Keep export endpoints canonical, use the Clipboard API with explicit fallback/error messaging, and test serialization independently from browser permissions. | Frontend engineer | Clipboard permission denied, unsupported rich clipboard, or content mismatch. | UI tests cover success/failure and downloaded/copied content matches canonical export. |
| R-20 | Accessibility and Japanese text layout may be deferred until too late. | Medium | Medium | Use semantic controls from the first web sprint, then run a dedicated hardening sprint for keyboard use, focus, contrast, wrapping, and narrow screens. | Frontend engineer | Unreachable controls, clipped Japanese text, color-only states, or missing labels. | Accessibility checklist and automated component checks pass in Sprint 51. |
| R-21 | The unspecified external provider creates schedule, privacy, procurement, and SDK uncertainty. | High | High | Keep the first 45 sprints provider-neutral; require a vendor ADR and approved data boundary at Sprint 46; use official documentation during implementation. | Product/security owner | Sprint 46 starts without a provider, credential contract, or external-data approval. | ADR-015 is superseded by an accepted vendor-specific ADR. |
| R-22 | Direct sending or mailbox integration could be pulled into the MVP and bypass approval safeguards. | Medium | High | Exclude send routes/providers from every MVP sprint, add an API-surface negative test, and document mailbox draft creation as post-MVP only. | Product owner | SMTP/Graph/Gmail dependency, send endpoint, or automatic delivery behavior appears. | Release audit confirms no delivery dependency or route and exports require approvals. |
| R-23 | Demo data could contain real company or supplier information. | Low | High | Use only the fictional examples named in the specification and review seed fixtures before commit. | Sprint implementer | Real email address, person, asset, supplier, or internal detail appears in fixtures. | Seed review confirms all data is fictional and documented as such. |
| R-24 | Local-only operation may be mistaken for production readiness or compliance. | Medium | High | State known limitations prominently; require company security, privacy, retention, deployment, and provider review before real confidential use; make no certification claims. | Product/security owner | README or UI implies approved handling of regulated/export-controlled/proprietary data. | Release documentation includes the required disclaimer and deployment review checklist. |
| R-25 | Concurrent edits or multiple browser tabs may overwrite newer draft data. | Medium | Medium | Include `updated_at` in write contracts and use optimistic concurrency (version or conditional update) for mutable drafts before email workflow completion. | Backend engineer | A stale PATCH succeeds over a newer email draft or translation edit. | Conflict integration tests return a clear 409-style error and preserve the newer record. |

## Review cadence

- Review this register at the start of each phase and in Sprint 57's release review.
- Add a risk when a sprint discovers a new ambiguity; do not hide it in a deviation note.
- Close a risk only when its closure condition is evidenced by tests, a recorded decision, or an accountable product/security sign-off.
- Escalate any new **High impact** privacy, data-loss, approval-bypass, or delivery risk before continuing the affected sprint.
